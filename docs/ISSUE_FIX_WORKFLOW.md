# 工单修复闭环流程

> 目标：把“运行报错 -> 自动工单 -> AI 修复 -> 人工验收 -> 合并发布”变成固定流程。  
> 适用对象：影刀开发、Python 开发、AI 编码代理、验收人。

## 1. 流程概览

```text
影刀运行
  -> Python 输出 runner_{run_id}.json
  -> 产生 warning / error / snapshot / 日志
  -> 系统异常生成工单
  -> AI 读取工单与 snapshot
  -> AI 修复 Python 代码并补测试
  -> 人工验收
  -> 合并发布
  -> 失败样本沉淀为回归资产
```

## 2. 工单触发条件

以下情况应进入修复闭环：

- `runner_{run_id}.json.status == "pending_fix"`
- `runner_{run_id}.json.status == "failed"` 且已定位为 Python 层问题
- 同类 warning 高频重复，已经影响业务稳定性
- 本地复现发现 Python 逻辑缺陷、规则缺失、依赖调用错误

以下情况不直接开 Python 修复工单：

- 纯影刀页面操作问题
- 账号权限、验证码、人工审批未通过
- 临时外部系统不可用且属于可重试场景

## 3. 工单必填字段

每个工单至少包含以下信息：

- `run_id`
- `status`
- `error_code`
- `exc_category`
- `crash_snapshot_path`
- `log_path`
- `input_file_path`
- `project`
- `branch`
- `复现步骤`
- `预期结果`
- `实际结果`

建议补充：

- `operator`
- `env`
- `source`
- `upstream_run_id`
- `related_issue`
- `impact_scope`

## 5. AI 修复时必须完成的四件事

AI 接手工单后，必须完成以下动作，缺一不可：

1. 读取工单、日志、`crash_snapshot` 和输入样例。
2. 定位 Python 修改点，并只在职责边界内修复。
3. 补或更新测试，至少覆盖本次问题和同类回归风险。
4. 给出验收命令、复现方式和结果说明。

没有测试的修复，不算完成。

## 6. AI 标准操作步骤

### 6.1 接单分析

- 读取工单字段
- 读取 `runner_{run_id}.json`
- 读取 `crash_snapshots/crash_{run_id}.json`
- 读取 `logs/run_{run_id}.log`
- 找到对应输入文件
- 判断问题归属是否仍在 Python 职责范围内

### 6.2 本地复现

- 使用对应 `input_{run_id}.json` 复现
- 如果工单无输入文件，先补最小复现样例
- 复现结果必须和工单现象一致，否则先修正文档或复现步骤

### 6.3 修复实现

- 优先做最小闭环修复
- 不顺手扩大改动面
- 不把业务判断塞回影刀
- 不引入真实密钥、个人路径、环境耦合

### 6.4 测试补齐

至少补以下一种：

- 单元测试
- 集成测试
- 输入样例回归测试

生产 bug 的最低要求：

- 原始失败样例转成回归测试
- 同类边界条件至少再补 1 个测试样例

### 6.5 交付说明

AI 交付时应说明：

- 改了什么
- 为什么这样改
- 运行了哪些验证
- 还剩什么风险或假设

## 7. 分支与发布规则

### 7.1 分支规则

- `main`：只放已验收通过、可发布版本
- `fix/{issue_id}`：每个 bug 单独修复分支
- `feat/{topic}`：新功能开发分支

默认要求：

- 不在运行时切换生产 Git 分支
- 影刀生产环境只运行已发布代码
- 一个工单对应一个修复分支，避免把多个 bug 混在一起

### 7.2 合并门槛

合并到 `main` 前必须：

- 测试全绿
- 对应输入样例本地复现通过
- 输出状态符合预期
- 验收人确认通过

### 7.3 发布后动作

修复合并后，按需要执行：

- 更新 `project.template.json` 中 `version`
- 或补充 changelog / 变更说明
- 通知影刀切换到新的已发布版本
- 评估是否需要重跑历史失败任务

## 8. 验收人与职责

### 8.1 AI

- 负责实现修复
- 负责补测试
- 负责更新说明文档

### 8.2 人工验收人

- 判断修复是否符合业务预期
- 检查是否改出了职责边界
- 检查是否满足合并门槛

### 8.3 影刀侧

- 只消费发布后的稳定版本
- 不在生产运行时临时切 Git
- 按 `runner_{run_id}.json` 的状态回收结果

## 9. 关闭工单后的知识沉淀

每个关闭工单都应沉淀一条记录，至少包含：

- 这是什么问题
- 属于哪个异常分类
- 为什么影刀处理不了，要交给 Python
- Python 具体怎么修
- 后续如何避免
- 是否新增了规则、样例、测试

建议形成：

- 异常样本库
- 回归测试集
- 需求拆分补充规则
- 常见故障排查手册

## 10. 完成定义

一个工单只有在同时满足以下条件时，才算真正关闭：

1. 问题已复现并定位。
2. Python 代码已修复。
3. 测试已补齐并通过。
4. 验收人确认通过。
5. 变更说明已更新。
6. 知识沉淀已完成。
