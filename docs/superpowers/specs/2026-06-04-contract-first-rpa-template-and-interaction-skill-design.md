# 契约优先版 RPA Python 开发模板与交互 Skill 设计

## 背景

当前模板已经把影刀、Python、AI 的基础职责边界划清：影刀负责页面操作、文件准备和调度，Python 负责业务处理、日志、异常分类和标准输出，AI 负责在 Code 项目内实现和维护业务代码、测试与文档。

随着真实业务接入，模板需要从“Python 工程模板”升级为“AI 业务实现模板”。升级重点不是引入复杂框架，而是让 AI 在写代码前先产出可审查的业务契约，让 RPA 开发者可以围绕业务路径、输入输出和验收点进行确认。

本设计采用“双层沉淀”：

- 开发模板负责承载契约、代码规范、示例、测试和验收要求。
- 交互 Skill 负责驱动 AI 与 RPA 开发者完成业务理解、边界对齐和契约生成。

核心交接对象是“业务契约”。

## 目标

1. 让 AI 接到业务需求后，先形成结构化业务契约，再进入实现。
2. 让 RPA 开发者主要通过契约、函数说明、输入输出样例和验收点完成审查。
3. 保持影刀、Python、AI 的职责边界稳定，减少 AI 临场发挥。
4. 支持运行失败后形成可供 AI 接手的修复上下文。
5. 保留人工验收、是否推送远程、是否合并分支的最终决策权。

## 非目标

1. 不引入重量级框架、插件机制或通用流程编排引擎。
2. 不改变 `runner.py` 的对外输出协议。
3. 不把影刀页面操作职责迁移到 Python。
4. 不要求 RPA 开发者深入阅读 Python 实现细节后才能验收。
5. 不自动推送远程分支或自动合并主分支。

## 总体设计

整体设计分为三层。

第一层是开发模板。它是项目内的标准落点，规定业务任务最终应该留下哪些文档、示例、handler、测试和验收记录。

第二层是交互 Skill。它是业务沟通过程的工作流，负责把模糊业务描述转化为可实现、可审查、可验收的业务契约。

第三层是业务契约。它连接模板和 Skill，记录一个业务任务的路由键、输入字段、输出结果、处理步骤、异常语义和验收标准。

推荐执行顺序：

1. 用户提出业务目标。
2. 交互 Skill 引导 AI 复述业务路径并对齐职责边界。
3. AI 产出业务契约草案。
4. 用户确认契约。
5. AI 按开发模板实现 handler、样例、测试和文档。
6. AI 输出验收摘要。
7. 人工决定是否推送、合并或上线。

## 开发模板优化范围

模板优化聚焦四个阶段。

### 第一阶段：契约层

新增或更新文档：

- `docs/任务设计模板.md`
- `docs/AI交付检查清单.md`
- `docs/处理器实现规范.md`
- `README.md`
- `docs/REQUIREMENT_TEMPLATE.md`
- `docs/ACCEPTANCE_CHECKLIST.md`

这一阶段要求每个新增业务任务在实现前明确：

- `tasks[].type`
- `payload` 字段名、类型、必填性、默认值和路径规则
- handler 职责说明
- 业务处理步骤
- 业务输出文件和结果摘要
- warning / error 场景
- 验收点

### 第二阶段：结构层

保留 `runner.py + core/entry.py + core/handlers/` 的主骨架，先文档化推荐模式，再按需要进行轻量代码调整。

结构层应明确：

- `core/entry.py` 只做任务路由和统一异常语义衔接。
- 真实业务 handler 放入 `core/handlers/` 或明确的业务模块。
- handler 只从 `task["payload"]` 读取业务参数。
- 路由键只来自 `tasks[].type`。
- 输出目录由 Python 创建，业务输出默认写到 `data/output/`。
- 未实现的非空 `tasks[].type` 必须返回系统异常，不允许假成功。

### 第三阶段：验收层

补充一个标准业务示例，展示完整链路：

- 示例 `input.json`
- 示例 handler
- 示例测试
- 示例业务输出
- 示例 `runner_{run_id}.json` 摘要
- 示例验收说明

验收重点从“实现细节是否写得复杂”转向“实现是否忠实对应业务路径和契约”。

### 第四阶段：自动修复闭环

新增或更新文档：

- `docs/自动修复闭环说明.md`
- `docs/ISSUE_FIX_WORKFLOW.md`

修复闭环应明确：

- 故障工单最少需要包含的上下文。
- AI 修复前必须读取的文档、输入、输出、日志和快照。
- AI 修复后必须交付的代码变更、测试结果和验收摘要。
- 人工确认、推送、合并和上线节点。

## 交互 Skill 设计

交互 Skill 的定位是“RPA 业务实现契约生成 Skill”。它不直接替代模板，也不直接承诺实现代码；它负责让 AI 和用户在实现前形成清晰业务契约。

Skill 工作流：

1. 业务复述：AI 用业务语言复述目标、对象、输入来源和期望结果。
2. 路径拆解：拆出主要业务步骤、分支、过滤规则和人工确认点。
3. 边界对齐：区分影刀、Python、人工、外部系统各自负责什么。
4. 输入设计：设计 `tasks[].type` 和 `payload` 字段。
5. 输出设计：设计业务输出文件、结果摘要和影刀消费字段。
6. 异常设计：定义 BusinessException、SystemException、retryable、pending_fix 的触发场景。
7. 验收设计：列出用户无需读实现细节也能检查的验收点。
8. 实现交接：将确认后的契约写入模板文档或任务设计稿，再进入开发实现。

Skill 的输出应是一份结构化业务契约草案，而不是直接生成业务代码。

## 业务契约结构

每个业务契约至少包含：

- 任务名称
- 任务类型 `tasks[].type`
- 业务目标
- 影刀职责
- Python 职责
- 人工确认点
- 输入文件和 `payload` 字段表
- 输出文件和 `results[].data` 摘要
- 业务步骤
- warning 场景
- system error 场景
- 测试样例
- 验收标准

## 实施顺序

推荐分四步实施：

1. 写入模板文档规范，先固定契约优先的协作方式。
2. 补充标准业务示例，让规范可读、可跑、可验收。
3. 轻量整理 handler 组织和入口路由推荐模式。
4. 创建交互 Skill，把业务契约生成流程沉淀为跨项目可复用能力。

这个顺序可以先让当前模板受益，再把稳定下来的流程抽象为 Skill，减少 Skill 与模板文档脱节的风险。

## 验收标准

设计落地后应满足：

1. AI 接到业务需求后，会先产出业务契约，而不是直接写 handler。
2. RPA 开发者可以通过契约、样例、测试摘要和交付清单完成主要审查。
3. 新业务实现能遵循统一目录、统一说明、统一结果摘要模式。
4. 未实现任务类型、业务 warning、系统异常和可重试异常都有清晰语义。
5. 运行失败后，模板能提供足够上下文让 AI 接手修复。
6. 人工仍保留推送、合并、上线的最终决策权。

## 风险与约束

1. 如果模板文档和 Skill 工作流重复维护，后续可能产生口径漂移。
2. 如果契约要求过重，小业务会感觉流程成本偏高。
3. 如果只做 Skill 而不改模板，契约缺少稳定落点。
4. 如果只改模板而不做 Skill，真实业务沟通仍依赖 AI 临场发挥。

控制方式：

- 模板保存稳定规范，Skill 保存交互步骤。
- 小业务允许生成轻量契约，但不得跳过 `type`、`payload`、输出、异常和验收。
- Skill 输出优先引用模板文档，不重复定义技术协议。
