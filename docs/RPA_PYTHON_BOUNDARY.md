# RPA / Python / AI 协作边界

> 适用范围：影刀 RPA + `run.bat` + `runner.py` + Python 业务模块 + AI 修复流程  
> 目的：把“谁负责什么”固化成硬规则，避免需求拆分时临时判断、职责漂移或 AI 越界修改。

## 1. 总原则

本项目采用“三层协作”：

1. 影刀负责 UI 编排和人与系统交互。
2. Python 负责业务执行、数据处理、规则判断和标准化输出。
3. AI 负责实现和修复 Python 代码，不直接接管影刀运行时流程。

默认规则：

- 能稳定通过标准输入输出协议完成的业务逻辑，优先放到 Python。
- 能明显依赖页面状态、账号状态、验证码、弹窗、人机交互的动作，放到影刀。
- AI 只能修改自己职责范围内的内容；没有明确要求时，不主动改影刀流程。

## 2. 硬边界

### 2.1 影刀负责

- 打开页面、登录、退出、切换账号
- 点击、输入、上传、下载、截图
- 等待页面加载、处理弹窗、处理验证码
- 人工确认节点和人机交互节点
- 调用 `run.bat`
- 读取 `runner_{run_id}.json`
- 按 `status` 做流程分支
- 触发重试、挂起、人工介入、回退到上游流程

### 2.2 Python 负责

- 读取 `input_{run_id}.json`
- 数据清洗、标准化、校验、去重、映射、格式转换
- Excel / CSV / JSON / 文本 / 文件解析
- 业务规则判断和结果计算
- API 请求、数据库读写、第三方依赖调用
- 异常编码、日志、`crash_snapshots/`、通知、工单信息组装
- 输出 `runner_{run_id}.json`
- 补充和维护自动化测试

### 2.3 AI 负责

- 根据需求模板实现 Python 代码
- 根据工单、日志、snapshot 修复 Python 代码
- 补充或更新测试
- 更新 README、变更说明、验收记录
- 沉淀规则、异常样本、回归测试

### 2.4 AI 不负责

- 代替影刀做人机交互判断
- 未经明确要求修改影刀 UI 流程
- 在运行时切换生产 Git 分支
- 引入真实密钥、生产账号、临时个人路径
- 跳过测试直接宣称修复完成

## 3. 需求拆分判断表

| 场景 | 默认归属 | 判断规则 |
|------|----------|----------|
| 页面打开、点击、输入、上传下载 | 影刀 | 依赖 UI 状态和浏览器上下文 |
| 验证码、弹窗、人工确认 | 影刀 | 依赖实时交互或人为决策 |
| 运行 Python 任务 | 影刀 | 统一通过 `run.bat` 调度 |
| 读取 `runner_{run_id}.json` 后分支 | 影刀 | 只消费标准状态，不解析技术细节 |
| Excel/CSV/JSON 解析 | Python | 结构化处理更适合代码和测试 |
| 字段映射、清洗、去重、聚合 | Python | 需要稳定逻辑和回归测试 |
| 业务规则判断 | Python | 需要可复现、可测试、可审计 |
| API / 数据库访问 | Python | 需要统一异常和日志 |
| 根因分析、修复建议、补测试 | AI | 建立修复闭环 |

## 4. 边界决策规则

需求拆分时，按以下顺序判断：

1. 这个动作是否需要直接操作页面或处理人机交互？
2. 这个动作是否能通过纯数据输入输出稳定复现？
3. 这个逻辑是否需要被测试、复用、追踪、回归？
4. 这个异常影刀是否只能看到现象，但无法稳定判定根因？

如果答案分别是：

- 第 1 条是“是”，优先放影刀。
- 第 2、3、4 条有任一“是”，优先放 Python。

当一个需求同时包含 UI 和业务逻辑时，拆成“两段式”：

1. 影刀完成数据获取、文件下载、页面动作。
2. Python 接收标准输入，完成业务处理并回传标准结果。

## 5. 影刀与 Python 的接口契约

### 5.1 输入契约

影刀在执行前写出 `input_{run_id}.json`，并通过 `run.bat` 调用：

```bat
run.bat {run_id} input_{run_id}.json
```

最少应包含：

- `run_id`
- `project`
- `tasks`
- `context.operator`
- `context.env`
- `context.source`

### 5.2 输出契约

Python 必须输出 `runner_{run_id}.json`，并保证顶层包含：

- `status`
- `message`
- `data.run_id`
- `data.results`
- `data.warnings`
- `data.errors`
- `data.retryable`
- `data.log_path`
- `data.crash_snapshot_dir`

### 5.3 状态消费原则

影刀只消费标准状态，不解析 Python 堆栈细节。

| `status` | 含义 | 影刀动作 |
|----------|------|----------|
| `success` | 全部完成 | 继续下游 |
| `warning` | 有警告但可继续 | 记录后继续 |
| `retryable_error` | 可重试系统异常 | 延迟后重试 |
| `pending_fix` | 已进入修复闭环 | 标记修复中并停止当前流程 |
| `failed` | 不可恢复失败 | 通知人工 |
| `locked` | 并发冲突 | 等待后重试 |
| `fatal` | 入口或配置级错误 | 终止并通知维护者 |

## 6. 边界升级规则

以下情况要把原本放在影刀里的逻辑迁回 Python：

- 同一逻辑开始在多个流程复用
- 同一判断条件越来越复杂
- 同类异常需要回归测试
- 影刀判断已经依赖大量 JSON 细节
- 需要基于错误码、分类、日志、snapshot 做自动修复

以下情况可以保留在影刀：

- 一次性临时页面操作
- 高度依赖网页状态、验证码或人工确认
- 没有稳定数据接口，且短期内不会复用

## 7. 交付要求

每个新需求开始前，必须先在需求描述里明确：

- 哪部分由影刀完成
- 哪部分由 Python 完成
- AI 是否只改 Python，还是允许联动修改文档/测试

如果边界不清，不进入编码阶段，先补齐需求模板。
